# Lua interface (buffered model responses)

Run with `cargo run -p artist -- -p "first prompt" "second prompt" --config path/to/config.lua` (or repeat `-p`). Prompts run in order using one conversation. Use `--model model-id` to select a model, `--list-models` for IDs, or `--list-models-json` for the metadata registry. `--reasoning level` selects a supported reasoning level. No provider is configured by default. See `configs/mock-model.lua` for a working configuration for the local mock API.

- `artist.provider({ name = "my-provider", models = {"model-a", "model-b"}, default_model = "model-a", adapter = "chat_completions", endpoint = "https://.../v1/chat/completions", auth = { bearer_env = "API_KEY" }, headers = { ["x-custom"] = "value" }, options = { temperature = 0.5 } })` registers one provider with multiple model IDs. `default_model` is optional if there is just one configured ID; otherwise choose with `--model`. `endpoint` defaults to OpenAI's endpoint. `auth.bearer_env` is resolved when making a request; header values may also be zero-argument Lua functions evaluated per request. See `configs/mock-model.lua` and `configs/opencode-go.lua`.
- Add `discover = { endpoint = "https://.../v1/models", filter = function(id) return ... end }` for optional OpenAI-style `GET /models` discovery (`data[].id`). `--list-models` fetches it and combines it with `models`; normal prompts also fetch the catalog once to resolve the selected model's metadata. `filter` is optional. Discovery does not prove that a model supports Chat Completions or tool calls: OpenCode Go's catalog includes models for Responses and Messages too. Use a filter or a hardcoded list to avoid offering incompatible models. Discovery pagination is not yet supported. For discovery-only providers, supply `default_model` or `--model`; no implicit first-model selection.
- `artist.provider({ name = "my-provider", models = {"model-id"}, request = function(context, tools, model_id) ... end, response = function(status, headers, body) ... end })` is the generic HTTP escape hatch and registers the provider. `request` returns `{url, method?, headers?, body, timeout?}`. Rust serializes `body` as JSON and sends it with `reqwest`. `response` receives a Rust-decoded JSON table and returns an array of `ModelEvent` tables (with `type` fields such as `text_delta`, `tool_call_start`, `tool_call_arguments_delta`, `tool_call_end`, `finished`). Non-2xx responses are passed to `response` too.
- To route models by protocol, add `adapters = { responses = { adapter = "openai_responses", endpoint = "https://.../v1/responses" }, messages = { adapter = "anthropic_messages", endpoint = "https://.../v1/messages", auth = { api_key_env = "KEY" }, options = { max_tokens = 8192 } } }` and `model_info = { ["model-b"] = { adapter = "responses" } }`. Unmapped models use the provider's default adapter; named adapters inherit provider auth and headers unless overridden; options are adapter-specific. Only `chat_completions`, `openai_responses`, and `anthropic_messages` are built in; all currently use buffered responses. Responses replays native output items (including encrypted reasoning); Messages replays signed content blocks. Do not strip these from context during tool turns.
- Model metadata can be configured using `model_info = { ["model-a"] = { context_window = 128000, max_output_tokens = 8192, reasoning_map = { high = "high", off = "none" }, default_reasoning = "high" } }`. A `reasoning_map` derives selectable levels from its keys and maps them to wire values. Chat Completions can also use `thinking_format = "deepseek"` and `requires_reasoning_content = true` per model. Metadata keys must match IDs in `models`. Unknown fields remain absent; an empty `reasoning_levels` list means no reasoning levels. For catalogs carrying this metadata, use `discover = { endpoint = "...", parse = function(body) return {{id = "...", context_window = ..., reasoning_levels = {...}}} end }`. The parser receives the decoded JSON body and must return an array of model descriptors. Explicit `model_info` fields override discovered fields. `--reasoning` validates against the selected model's registry entry, then Chat Completions sends `reasoning_effort`; generic Lua `request` gets `reasoning_level` as its fourth argument. A `model_info` event announces the selected model and known metadata. APIs may reject a level even when configured if their support changes.
- `configs/opencode-go.lua` keeps its Pi-sourced model snapshot in the same file. The snapshot contains no prices; unknown live IDs have no cataloged metadata and use the default adapter.
- `artist.model({...})` remains as a compatibility alias for a single-model provider.
- Optional `cost = function(model_id, usage) ... end` on `artist.provider` returns a nonnegative USD amount for one response, or `nil` if pricing is unknown. `usage` has `input_tokens`, `output_tokens`, and optional `cached_input_tokens`, `cache_write_input_tokens`, and `reasoning_output_tokens`. Cached/reasoning tokens are subsets of the input/output totals. The emitted `usage` event includes `cost_usd` when supplied; it remains absent otherwise. A generic Lua adapter may return `cost_usd` directly in its usage event, which takes precedence over the calculator.
- `artist.register_tool({name, description, parameters, execute = function(args, ctx) ... end})` registers a tool. `parameters` is JSON Schema; `ctx.cwd` is the current working directory. `execute` returns a string or `{text, is_error?}` and may call async native functions.
- Bundled `src/default.lua` defines and registers each built-in tool's schema individually. Its callbacks run the Rust implementations through `artist.native.execute(name, args, cwd)`. User tools use the same `artist.register_tool` API. `artist.unregister_tool("write")` removes a registered tool, so it is neither advertised nor dispatched; an unknown name is an error.
- `artist.set_system_prompt(text_or_function)` replaces the base prompt; `artist.append_system_prompt(text_or_function)` appends a section. Functions receive `{model_name, cwd}`. Bundled `src/default.lua` sets the default prompt, and user config runs afterward. The composed prompt is stored once for the conversation.
- `artist.select_context(function(conversation) ... end)` optionally returns a `ContextSelection` table before each request; fields include `include_system_prompt`, `included_entries`, and `included_blocks`. Omit it to include all history. Selection does not mutate the stored conversation.
- `artist.json.decode(string)` and `artist.json.encode(value)` use Rust's JSON implementation. JSON null is `artist.json.null` in Lua, not `nil`.

The first slice uses complete JSON responses; model streaming decoding is not wired yet. `artist -p` writes newline-delimited JSON events to stdout. Lua config files are trusted code.
